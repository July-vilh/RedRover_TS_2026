## 1. Объект как параметр функции

**Зачем.** Параметры функции мы уже типизировали: `name: string`. Если параметр — объект, типизировать его «как обычно» внутри фигурных скобок не получится: TypeScript поймёт запись совсем иначе.

### Ловушка

```ts
function getUser({ firstName: string, lastName: string }) {
  // ...
}
// error TS2300: Duplicate identifier 'string'.
// error TS7031: Binding element 'string' implicitly has an 'any' type.
```

Здесь хотели сказать «`firstName` — строка». А TypeScript прочитал это как **деструктуризацию с переименованием** (см. [раздел 2](#2-деструктуризация)): «возьми из объекта `firstName` и положи в переменную с именем `string`». Отсюда две ошибки: две переменные с одинаковым именем `string`, и у них нет типа.

### Базовый синтаксис

Тип объекта всегда пишется **после двоеточия**, отдельными фигурными скобками. Слева от двоеточия — два варианта:

```ts
// 1. Деструктуризация: сразу достаём нужные свойства в переменные
function имя({ ключ1, ключ2 }: { ключ1: тип1; ключ2: тип2 }): типРезультата {
  // ключ1, ключ2
}

// 2. Объект целиком под одним именем
function имя(параметр: { ключ1: тип1; ключ2: тип2 }): типРезультата {
  // параметр.ключ1, параметр.ключ2
}
```

### Пример

Вариант лектора — с деструктуризацией:

```ts
function getUser({ firstName, lastName }: { firstName: string; lastName: string }): string {
  return `Hello, my name is ${firstName} ${lastName}.`;
}

console.log(getUser({ firstName: "Bob", lastName: "Vila" })); // Hello, my name is Bob Vila.
```

То же самое с объектом целиком:

```ts
function getUser(user: { firstName: string; lastName: string }): string {
  return `Hello, my name is ${user.firstName} ${user.lastName}.`;
}

console.log(getUser({ firstName: "Bob", lastName: "Vila" })); // Hello, my name is Bob Vila.
```

Вызов и результат одинаковые. Разница только внутри функции:

| | `{ firstName, lastName }: {...}` | `user: {...}` |
|---|---|---|
| Обращение внутри | `firstName` | `user.firstName` |
| Доступ к объекту целиком | нет — только к вынутым свойствам | есть: можно передать `user` дальше, вывести в лог |
| Удобно, когда | нужны 1–3 свойства | нужен весь объект или много свойств |



## 2. Деструктуризация

**Зачем.** В объекте 15–20 свойств, а нужны два. Или ключи названы неудобно (старый код, чужой API), и хочется работать с понятными именами. Деструктуризация (destructuring) вынимает нужные свойства в отдельные переменные.

### Базовый синтаксис

```ts
const { ключ1, ключ2 } = объект;                   // переменные с именами ключей
const { ключ1: новоеИмя1, ключ2: новоеИмя2 } = объект; // с переименованием
const { вложенный: { ключ } } = объект;             // из вложенного объекта
```

Слева от двоеточия — ключ в объекте, справа — имя новой переменной.

### Пример

```ts
const user = { firstName: "John", lastName: "Smith", occupation: "teacher", age: 40 };

const { firstName: first, lastName: last } = user;
console.log(first, last); // John Smith

const { firstName, age } = user;
console.log(firstName, age); // John 40
```

`occupation` мы не взяли — он просто не попал в переменные.

Лектор уточнил по вопросу студента: деструктуризация **не создаёт новый объект**, хотя запись похожа на объект. Получаются обычные отдельные переменные — то же самое, что написать `const firstName = user.firstName; const age = user.age;`. Дать «имя» этому набору нельзя. Если нужен новый объект — соберите его из переменных отдельно.

Пример из автотестов — достать из ответа API только то, что проверяете:

```ts
const response = { status: 200, data: { id: 7, email: "qa@test.com", roles: ["admin"] } };

const { status, data: { email } } = response;
console.log(status, email); // 200 qa@test.com
```

**Как часто используется.** Лектор сказал, что нечасто: в своём коде объекты обычно сразу проектируют удобно. Деструктуризация нужна, когда объект пришёл извне — из API, базы данных или старого кода, который нельзя менять, потому что от него зависит всё остальное.


## 3. Интерфейс (interface)

**Зачем.** Писать тип объекта прямо в объявлении (`const car: { brand: string; ... }`) долго. Для объекта с десятком свойств и вложенными объектами легко ошибиться. А если таких объектов несколько, тип придётся дублировать.

**Интерфейс** — это шаблон, описание структуры объекта: какие у него свойства и каких они типов. Лектор сравнил его с меню в ресторане: видно, какие есть блюда и из чего они, но не видно, откуда продукты и как их готовят. Интерфейс говорит, *что* будет в объекте, но не содержит значений.

### Базовый синтаксис

```ts
interface ИмяИнтерфейса {
  ключ1: тип1;
  ключ2?: тип2;   // опциональное
}

const переменная: ИмяИнтерфейса = { ключ1: значение1 };
```

- Ключевое слово `interface`, имя — с большой буквы.
- После имени сразу фигурные скобки, **без** знака `=`.
- Свойства разделяются `;`.

### Пример

```ts
interface Car {
  brand: string;
  model?: string;
  year: number;
}

const myCar: Car = { brand: "Toyota", year: 2020 };
myCar.model = "Corolla"; // model опциональный — можно добавить позже
```

Всё, что мы делали с типами объектов в прошлой лекции (опциональные свойства, вложенные объекты, добавление опциональных свойств позже), работает и с интерфейсами.

Один интерфейс можно использовать для многих объектов: `const car1: Car = ...`, `const car2: Car = ...`. В этом его главное преимущество перед типом, записанным прямо у переменной.

Студент заметил, что интерфейс похож на класс. Лектор согласился и сказал, что это не случайно — к классам вернутся позже.

## 4. Методы в интерфейсе

В интерфейсе описывается только **сигнатура** метода (signature — имя, параметры с типами и тип результата). Тело метода, то есть реализация, пишется в самом объекте.

### Базовый синтаксис

```ts
interface Имя {
  метод1(параметр: тип): типРезультата;         // запись как у метода
  метод2: (параметр: тип) => типРезультата;     // запись через стрелку
}
```

Обе формы в интерфейсе означают одно и то же.

### Пример

```ts
interface Car {
  brand: string;
  year: number;
  greet(name: string): string;
  getDescription: () => string;
}

const myCar: Car = {
  brand: "Toyota",
  year: 2020,
  greet(n) {
    return `Hello ${n}, I am ${this.brand}`;
  },
  getDescription: () => "A car",
};

console.log(myCar.greet("John"));     // Hello John, I am Toyota
console.log(myCar.getDescription());  // A car
```

Два наблюдения из разбора на лекции:

- **Типы в реализации можно не повторять.** В интерфейсе уже сказано, что `greet` принимает `string` и возвращает `string`. TypeScript берёт типы оттуда: `greet(n)` компилируется без ошибок, и `n` получает тип `string`. Повторять тип — полное дублирование (один из студентов это и заметил).
- **Имя параметра в реализации может отличаться** от имени в интерфейсе: в интерфейсе `name`, в объекте `n`. Работает, потому что при вызове важен порядок параметров, а не их имена. Лектор советует для читаемости оставлять те же имена.

`this` внутри метода работает так же, как в прошлой лекции: `this.brand` — свойство объекта, у которого вызван метод.

## 5. readonly — свойство только для чтения

**Зачем.** Некоторые значения после создания объекта не должны меняться: VIN-номер машины, id пользователя, id заказа.

### Базовый синтаксис

```ts
interface Имя {
  readonly ключ: тип;                    // нельзя присвоить новое значение
  readonly массив: readonly тип[];       // нельзя ни присвоить, ни изменить содержимое
}
```

### Пример

```ts
interface Vehicle {
  readonly vin: number;
  mileage: number;
}

const v: Vehicle = { vin: 123, mileage: 10 };
v.mileage = 500; // OK
v.vin = 999;
// error TS2540: Cannot assign to 'vin' because it is a read-only property.
```

### Подводный камень: массивы

`readonly` перед свойством запрещает только **присваивание** нового массива. Метод `push` меняет существующий массив, и это не запрещено:

```ts
interface Vehicle { readonly emails: string[] }
const v: Vehicle = { emails: ["a@a"] };

v.emails = ["x"];
// error TS2540: Cannot assign to 'emails' because it is a read-only property.

v.emails.push("b@b"); // компилируется!
console.log(v.emails); // [ 'a@a', 'b@b' ]
```

Лектор назвал это «лазейкой» (loophole). Чтобы закрыть её, `readonly` ставят второй раз — перед типом массива:

```ts
interface Vehicle { readonly emails: readonly string[] }
const v: Vehicle = { emails: [] };

v.emails.push("x");
// error TS2339: Property 'push' does not exist on type 'readonly string[]'.
```

Второй `readonly` (перед типом) работает только с массивами и кортежами.

### readonly — только проверка TypeScript

Лектор подчеркнул: это ошибка **TypeScript**, а не JavaScript. В JavaScript понятия `readonly` нет. По умолчанию `tsc` выдаёт ошибку, но всё равно создаёт `.js`-файл, и тот запускается и меняет значение.

Как этого избежать:

- **Флаг `noEmitOnError: true`** в `tsconfig.json` (лектор упомянул «флаг в конфигурации», но не назвал его). С ним `tsc` не создаёт `.js`, если есть ошибки типов. Проверено: без флага файл создаётся и выполняется, с флагом — не создаётся.
- **Уточнение. `Object.freeze`** — защита на уровне JavaScript, работает во время выполнения:

```ts
const frozen = Object.freeze({ vin: 1 });
(frozen as any).vin = 2;
// TypeError: Cannot assign to read only property 'vin' of object '#<Object>'
```

`Object.freeze` «поверхностный»: вложенные объекты и массивы остаются изменяемыми.

Для тестов это полезно, когда общие тестовые данные (test data) не должны меняться одним тестом так, что сломается другой — `readonly` и `Object.freeze` помогают сохранить изоляцию тестов.

## 6. Переоткрытие интерфейса

Если объявить интерфейс с тем же именем ещё раз, TypeScript **объединит** оба объявления в один интерфейс. Лектор назвал это «переоткрытием». Официальный термин — **declaration merging** (слияние объявлений).

```ts
interface User { name: string; email: string }
interface User { age: number }   // добавили свойство «снаружи»

const u: User = { name: "A", email: "a@a" };
// error TS2741: Property 'age' is missing in type '{ name: string; email: string; }' but required in type 'User'.
```

Теперь `User` требует все три свойства. Если во втором объявлении сделать `age?: number`, его можно не указывать.

Ограничения:

- Одно и то же свойство можно объявить повторно только **с тем же типом**:

```ts
interface U { name: string }
interface U { name: number }
// error TS2717: Subsequent property declarations must have the same type.
// Property 'name' must be of type 'string', but here has type 'number'.
```

- В одном интерфейсе свойство не может повторяться — `Duplicate identifier`.
- **Значений по умолчанию в интерфейсе нет** (вопрос студента). Интерфейс описывает только типы, значения живут в объекте:

```ts
interface U { age: number = 10 }
// error TS1246: An interface property cannot have an initializer.
```

**Уточнение.** Помимо переоткрытия, интерфейс можно **расширить** через `extends` — создать новый интерфейс на основе существующего. На лекции этого не было, но на практике это встречается чаще, чем переоткрытие:

```ts
interface Admin extends User { permissions: string[] }
const ad: Admin = { name: "Root", email: "r@r", age: 50, permissions: ["all"] };
```

## 7. Type alias — собственный тип

Второй способ вынести тип объекта отдельно. Лектор назвал его «кастомные типы». Официальное название — **type alias** (псевдоним типа). Работает очень похоже на интерфейс.

### Базовый синтаксис

```ts
type ИмяТипа = {
  ключ1: тип1;
  ключ2?: тип2;
};
```

Отличия записи от интерфейса: слово `type`, знак `=` после имени и `;` в конце.

### Пример

```ts
type User = { name: string; age: number; email?: string };

const u1: User = { name: "John", age: 30 };
const u2: User = { name: "Kate", age: 25, email: "k@k" };
```

Одинаковые ключи, разные значения — для этого тип и нужен.

Всё, что умеет интерфейс для объектов, `type` тоже умеет: опциональные свойства, методы, `readonly` (в том числе `readonly string[]`).

**Тип существует только для TypeScript.** Студенты спросили, что выведет `typeof`:

```ts
console.log(typeof u1);   // object — в JavaScript это обычный объект
console.log(typeof User);
// error TS2693: 'User' only refers to a type, but is being used as a value here.
```

После компиляции в JavaScript от `type` и `interface` ничего не остаётся. Во время выполнения их нет.

## 8. Функция, которая создаёт объекты

**Зачем.** Если нужно создать 100 пользователей с 20 свойствами каждый, писать 100 объектов вручную долго, и в каком-нибудь обязательно пропустишь свойство. Функция создаёт объект по заданному типу, а вызывать её можно сколько угодно.

```ts
type User = { name: string; age: number; email?: string };

function createUser(name: string, age: number, email: string): User {
  return { name: name, age: age, email: email };
}

const user1 = createUser("Bob", 22, "bob@test.com");
console.log(user1); // { name: 'Bob', age: 22, email: 'bob@test.com' }
```

Из вопросов студентов:

- В `return { name: name, ... }` слева — **ключи**, они должны совпадать с типом `User`, переименовать их нельзя. Справа — **параметры** функции, их можно назвать как угодно.
- Тип результата (`: User`) TypeScript выведет сам, если его не указать. Но лектор просит пока указывать всегда. Когда станет понятнее, как работает TypeScript, будем решать, где его можно опускать.
- Можно сначала создать объект в переменной (`const obj: User = {...}`), потом вернуть его. Работает, но просто длиннее.

**Уточнение.** Если параметр называется так же, как ключ, пишут сокращённо: `return { name, age, email };` — это то же самое, что `{ name: name, age: age, email: email }`.

Для автотестов это обычный приём: функция, создающая тестовые данные (test data factory), например `createUser({ role: "admin" })`. Тесты перестают зависеть от десятков вручную написанных объектов.

## 9. Объединение типов: & и |

### Базовый синтаксис

```ts
type Новый = ТипА & ТипБ;             // intersection: все свойства обоих типов
type Новый = ТипА & { ключ: тип };    // добавить свойство к существующему типу
type Новый = ТипА | ТипБ;             // union: либо один тип, либо другой (или оба)
```

### & — пересечение (intersection)


```ts
type User = { name: string; age: number; email?: string };
type Occupation = { title: string; salary?: number };

type VipUser = User & { label: string };
const v: VipUser = { name: "V", age: 2, label: "gold" };

type Bio = User & Occupation;
const b: Bio = { name: "A", age: 1, title: "QA" };
```

Обязательные свойства обоих типов нужно указать все:

```ts
const b: Bio = { name: "A", age: 1 };
// error TS2322: Type '{ name: string; age: number; }' is not assignable to type 'Bio'.
// Property 'title' is missing in type '{ name: string; age: number; }' but required in type 'Occupation'.
```

Переоткрывать `type`, как интерфейс, нельзя — второе объявление с тем же именем даст `Duplicate identifier`. Для типов новые свойства добавляют через `&`, создавая новый тип.

Порядок в `User & Occupation` не важен. Лектор советует держать его одинаковым с порядком свойств в объекте — для читаемости.

### | — объединение (union)

Тот же union, что был для примитивов (`string | number`), только для объектов:

```ts
type Bio2 = User | Occupation;

const x1: Bio2 = { name: "A", age: 1 };              // как User
const x2: Bio2 = { title: "QA" };                    // как Occupation
const x3: Bio2 = { name: "A", age: 1, title: "QA" }; // тоже можно — подходит под оба
```

Лектор: `|` нужен, когда заранее неизвестно, какой из вариантов придёт, — чаще всего это ответы API. Если на самом деле нужны свойства обоих типов, пишите `&`, а не `|`. Технически `|` тоже пропустит объект со всеми свойствами (`x3`), но код будет вводить в заблуждение того, кто придёт после вас.

**Уточнение — чем `|` неудобен на практике.** К свойству, которое есть только в одном из вариантов, TypeScript не даст обратиться напрямую:

```ts
const b = { title: "QA" } as User | Occupation;
console.log(b.title);
// error TS2339: Property 'title' does not exist on type 'User | Occupation'.
```

Сначала нужно проверить, какой вариант пришёл (это называется сужением типа, narrowing):

```ts
if ("title" in x2) console.log(x2.title); // QA
```

### Вопрос про Student & Teacher

Студент спросил, можно ли объединить через `&` два типа, где у обоих есть `name`. Лектор ответил «нет, ты путаешь с классами».

**Уточнение.** Можно, если у свойства одинаковый тип:

```ts
type Student = { name: string; grade: number };
type Teacher = { name: string; subject: string };

const st: Student & Teacher = { name: "Ann", grade: 5, subject: "Math" }; // OK
```

Проблема возникает, только если типы свойства **разные**. Тогда свойство получает тип `never` (never — тип, у которого нет ни одного допустимого значения), и объект создать невозможно:

```ts
type A = { id: string };
type B = { id: number };
const x: A & B = { id: 1 };
// error TS2322: Type 'number' is not assignable to type 'never'.
```

## 10. interface или type

«Самый популярный вопрос», по словам лектора. Ответ: сегодня они работают очень похоже, и в 80–90% случаев разницы нет.

| | `interface` | `type` |
|---|---|---|
| Описать объект | да | да |
| Опциональные свойства, методы, `readonly` | да | да |
| Добавить свойства позже | переоткрытие или `extends` | только новый тип через `&` |
| Union (`A \| B`), literal union, примитивы | нет | да |

Когда что выбирать:

- **interface** — если заранее известно, что свойства будут добавляться. Например, API со временем присылает новые поля.
- **type** — если структура известна и меняться не будет, а также когда нужны `&` и `|`.
- Часто решает не техника, а договорённость команды: «у нас только интерфейсы» — значит, только интерфейсы.


## 11. Итог двух лекций: объекты и начало ООП

Лектор подвёл итог темы объектов:

- Объект хранит данные (свойства) и действия (методы).
- Методы обращаются к свойствам своего объекта через `this`. Значение `this` определяется в момент вызова. У стрелочных функций своего `this` нет — он берётся у внешней функции.
- Типы объектов лучше выносить в `interface` или `type`, особенно когда свойств много.
- Код теперь пишется не просто строчка за строчкой: функции разделяют код по задачам, объекты описывают данные и взаимодействуют друг с другом. Этот подход — начало **объектно-ориентированного программирования** (ООП, OOP). Его принципы будут разбирать на следующих лекциях.

## 12. Literal union — выбор из конкретных значений

**Зачем.** Union `string | number` разрешает любую строку или любое число. А иногда допустимы только конкретные значения: размер картинки `small` или `large`, направление `up`/`down`/`left`/`right`.

### Базовый синтаксис

```ts
let переменная: "значение1" | "значение2" | "значение3";
let код: 200 | 404 | 500;          // числа тоже можно
```

### Пример

```ts
let picture: "small" | "large" = "small";
picture = "large";  // OK

picture = "medium";
// error TS2322: Type '"medium"' is not assignable to type '"small" | "large"'.
```

Студент спросил, почему ошибка говорит о *типах*, а не о значениях. Здесь `"small"` — это одновременно значение и тип: тип, в котором допустимо только одно значение. Отсюда название — literal type (литеральный тип).

Удобно вынести такой список в `type`:

```ts
type Browser = "chromium" | "firefox" | "webkit";
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
```

Именно так в Playwright описаны, например, имена браузеров. Опечатку `"chrome"` вместо `"chromium"` компилятор поймает до запуска тестов.

## 13. Enum — перечисление

**Enum** (enumeration, перечисление) — список именованных констант. Похож на literal union, но возможностей у него больше.

### Базовый синтаксис

```ts
enum Имя {
  Значение1 = 1,     // значения можно задать явно
  Значение2 = 2,
}

enum Имя2 { А, Б, В }          // без значений: 0, 1, 2
enum Имя3 { А = 10, Б, В }     // от 10: 10, 11, 12
enum Имя4 { А = "a", Б = "b" } // строковые — задавать все

let переменная: Имя = Имя.Значение1;
```

Имена членов пишут с большой буквы.

### Пример

```ts
enum Picture { Small = 1, Medium = 2, Large = 3 }

let pic: Picture = Picture.Small;
console.log(pic); // 1
```

Если после `Picture.` поставить точку, редактор предложит список допустимых значений. Несуществующее — ошибка:

```ts
let p: Picture = Picture.ExtraLarge;
// error TS2339: Property 'ExtraLarge' does not exist on type 'typeof Picture'.
```

### Числовые значения

Если значения не указаны, их проставляет TypeScript — от 0 по порядку. Если задать первое, остальные продолжат счёт:

```ts
enum Auto { Small, Medium, Large }        // Auto.Large  === 2
enum From10 { Small = 10, Medium, Large } // From10.Large === 12
```

Зачем задавать числа явно? Чтобы сравнивать с другими значениями:

```ts
let num: number = 5;
console.log(num === Picture.Large ? "equal" : "not equal"); // not equal (Large = 3)
```

Если значения не важны — нужно просто ограничить выбор, — их не указывают.

Строковые enum тоже есть, но в них значение нужно задать **каждому** члену:

```ts
enum Str { Small = "S", Medium, Large }
// error TS1061: Enum member must have initializer.
```

### Ограничить enum несколькими значениями

```ts
enum Direction { Up, Down, Left, Right }

let dir: Direction.Up | Direction.Down = Direction.Up; // OK
dir = Direction.Right;
// error TS2322: Type 'Direction.Right' is not assignable to type 'Direction.Up | Direction.Down'.
```

### Что такое enum во время выполнения

Студент спросил, не объект ли это. Лектор ответил «забудь про объекты, это совсем другой тип данных».

**Уточнение.** С точки зрения TypeScript enum — отдельный тип. Но в отличие от `type` и `interface`, enum **остаётся в JavaScript**: компилятор превращает его в обычный объект.

```ts
console.log(Picture);
// { '1': 'Small', '2': 'Medium', '3': 'Large', Small: 1, Medium: 2, Large: 3 }
console.log(typeof Picture); // object
console.log(Picture[3]);     // Large — обратное отображение: из числа в имя
```

### Почему многие не используют enum

Лектор: enum появился в TypeScript, в JavaScript его нет. При компиляции он превращается в сложный код, и при «глубоком» использовании возможны проблемы. Поэтому многие предпочитают типы. Сам лектор считает, что enum можно использовать, если применять аккуратно — для простого выбора из списка.

Будут ли enum в автоматизации на курсе? Лектор не уверен, скорее нет. Но теперь мы знаем, что они существуют.

## 15. Шпаргалка и типичные ошибки

### Синтаксис

```ts
// Объект как параметр
function f(user: { name: string; age?: number }): string { return user.name; }
function g({ name, age }: { name: string; age?: number }): string { return name; } // с деструктуризацией

// Деструктуризация
const { name, age } = user;
const { name: userName } = user;          // с переименованием
const { data: { email } } = response;     // из вложенного

// Interface
interface Car {
  readonly vin: number;
  brand: string;
  model?: string;
  emails: readonly string[];
  greet(name: string): string;
  describe: () => string;
}
interface Car { color?: string }          // переоткрытие (слияние)
interface Admin extends User { permissions: string[] } // расширение

// Type alias
type User = { name: string; age: number; email?: string };
type VipUser = User & { label: string };  // intersection
type Bio = User & Occupation;
type Response = Success | Failure;         // union

// Literal union
type Size = "small" | "medium" | "large";

// Enum
enum Picture { Small = 1, Medium, Large } // 1, 2, 3
enum Auto { A, B, C }                      // 0, 1, 2
let p: Picture = Picture.Small;
```

### Где какой знак

| Запись | Значение |
|---|---|
| `{ a: b } = obj` (слева от `=`) | деструктуризация: ключ `a` → переменная `b` |
| `x: { a: string }` | тип объекта |
| `interface X { }` | без `=` |
| `type X = { };` | с `=` и `;` |
| `A & B` | все свойства A и B |
| `A \| B` | либо A, либо B (или оба) |
| `readonly x: T[]` | нельзя присвоить новый массив |
| `readonly x: readonly T[]` | нельзя и присвоить, и изменить содержимое |

### Literal union или enum

| | Literal union | Enum |
|---|---|---|
| Запись | `"small" \| "large"` | `enum Size { Small, Large }` |
| Использование | `"small"` | `Size.Small` |
| Остаётся в JavaScript | нет | да, как объект |
| Числовые значения, сравнение | нет | да |
| Node.js strip-types | работает | не поддерживается |

### Типичные ошибки

1. **Тип объекта-параметра внутри деструктуризации.** `function f({ name: string })` — это переименование, а не тип. TS2300 и TS7031.
2. **Параметр-объект вообще без типа.** `function f(user)` — TS7006 в строгом режиме.
3. **Деструктуризация «создаёт объект».** Нет — создаются отдельные переменные.
4. **`readonly` на массиве без второго `readonly`.** `push` пройдёт.
5. **`readonly` как защита во время выполнения.** По умолчанию `tsc` создаёт `.js` даже с ошибками. Нужен `noEmitOnError` или `Object.freeze`.
6. **Переоткрытие интерфейса с другим типом свойства.** TS2717.
7. **Значение по умолчанию в интерфейсе.** TS1246 — значения только в объекте.
8. **Повторное объявление `type` с тем же именем.** `Duplicate identifier` — используйте `&`.
9. **`typeof` на типе.** TS2693 — типов нет во время выполнения.
10. **`|` там, где нужен `&`.** Компилируется, но вводит в заблуждение.
11. **Обращение к свойству одного из вариантов union без проверки.** TS2339 — сначала `"ключ" in obj`.
12. **Одно свойство с разными типами в `A & B`.** Тип свойства становится `never`.
13. **Строковый enum с незаданными значениями.** TS1061.
14. **Enum при запуске через Node.js strip-types.** `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`.
